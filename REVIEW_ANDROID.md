## 1. Краткий вывод

**Это функционально насыщенный прототип, но пока не отказоустойчивый Android-загрузчик.** Внешне понятное разделение на UI, service, engine и model не обеспечивает реального разделения ответственности: состояние задач, файловая система, потоки, сетевые операции и UI связаны через общие изменяемые объекты.

Главные препятствия для стабильного использования:

1. **Пауза автоматически запускает ту же задачу снова.** Отмена/удаление способны нарушить последовательность очереди и запустить несколько workers одновременно.
2. **Незавершённое аудио принимается за готовое**, а остатки кэша после перезапуска могут попасть в другую задачу.
3. **Нет безопасной публикации файлов:** совпадающие названия перезаписываются, частичные результаты пишутся прямо под итоговым именем.
4. **Выбор папки не работает; настройки, включая «только Wi‑Fi», не применяются.** Работа с публичным хранилищем не реализована корректно для всего заявленного диапазона Android.
5. **Финальная сборка теряет субтитры**, а Mix обрывает звук на длительности более короткой дорожки.
6. **Нет сохранения очереди и полноценного управления жизненным циклом службы.** Повтор ошибки может идти уже без foreground-режима.
7. **Миниатюры повторно скачиваются при обновлении прогресса**, создавая лишние потоки, трафик и риск нехватки памяти.
8. **Нет Android-тестов и Android CI.** README описывает другую, уже несуществующую архитектуру.

### Текущий поток

```text
MainActivity → ParamsFragment → новый DownloadEngine.fetchInfo()
                   ↓ mutable DownloadTask
              DownloadService.enqueue()
                   ↓ новый Thread на задачу
              один общий DownloadEngine
                   ├─ VotClient → HTTP перевода
                   ├─ yt-dlp → исходное видео/аудио
                   ├─ ProcessBuilder → FFmpeg
                   ├─ прямые File-записи в Download/ytrd
                   └─ HistoryManager → history.json
                   ↓ изменения того же DownloadTask + callback
              Service → Notification / DownloadsFragment
```

### Что сделано хорошо

- Размер кодовой базы пока позволяет провести локальный, постепенный рефакторинг без переписывания приложения.
- Семантические названия классов и пакетов, явный enum состояний, сравнительно простой последовательный сценарий загрузки.
- Сервис выделен из Activity; приложение не полагается только на жизненный цикл экрана.
- Внешние команды формируются списками аргументов, без `shell=True`/склейки shell-команды.
- HTTP `Response` и многие потоки закрываются через try-with-resources.
- Есть timeouts VOT, bounded polling, обработка ряда ошибок, throttling прогресса/уведомлений.
- Наличие `analysisGeneration` защищает от части устаревших результатов анализа ссылки.
- HistoryManager синхронизирует свои операции и отдаёт копию списка, хотя не глубокую копию элементов.
- Для открытия файлов применяется FileProvider и временное разрешение чтения; service/provider не экспортированы, cleartext отключён.
- Wrapper присутствует, версии зависимостей фиксированы, Gradle-настройки учитывают слабую машину.

### Главные нарушения границ

- `DownloadEngine.execute()` — около 260 строк и сразу несколько независимых обязанностей. Его сложно протестировать без файловой системы, Android Context, сети и процессов.
- `DownloadTask` одновременно request, runtime state, progress, результат и UI formatting. `outputPath` означает сначала **каталог назначения**, затем **готовый файл**.
- Service и engine оба изменяют `state`, а публичные поля позволяют UI наблюдать несогласованные промежуточные данные.
- Нет единственного владельца очереди: main thread и download threads вызывают `processNext()` и меняют `current`.
- UI напрямую создаёт сетевые клиенты, потоки, удаляет файлы, обновляет yt-dlp и чистит рабочий кэш.
- Статические синглтоны и прямые конструкторы мешают подменять зависимости; общая cancellation-сессия engine не привязана к задаче.

## 4. Существенные дефекты P1

### R01. «Пауза» автоматически возобновляет загрузку — [Проверено]

**Где:** [DownloadService.java](app/src/main/java/io/github/idex/ytrdroid/service/DownloadService.java), строки 31, 113–124, 155–165, 225–240.

`pauseCurrentTask()` отменяет выполнение, обнуляет `current`, кладёт задачу обратно в ту же очередь и немедленно вызывает `processNext()`. Планировщик не исключает `PAUSED`. Если других задач нет, начинается повторное выполнение той же задачи. Если есть — пауза действует только до её очереди, без команды пользователя. `isPaused` никогда не устанавливается в `true`, поэтому notification action не переключается корректно на «Продолжить».

**Проверка:** точные тела `pauseCurrentTask()` и `processNext()` извлечены из исходника в JVM-harness; Android notification и engine заменены заглушками, выполнение удерживалось latch. Получено:

```text
After pause of sole task, starts=[1, 1], state=DOWNLOADING
```

Это проверка планирования, не device-тест всей службы.

**Исправление:** отдельно определить семантику «пауза задачи» и «пауза всей очереди»; paused-задания не должны выбираться планировщиком. Следующий worker запускать только после подтверждения остановки предыдущего. UI и notification строить из одного состояния scheduler.

**Регрессия:** одна задача, три задачи, пауза на каждом этапе; paused не запускается до resume.

### R02. Отмена/удаление создают параллельные workers и ломают владельца процесса — [Проверено + Код]

**Где:** `service/DownloadService.java:101–110,137–183`; `engine/DownloadEngine.java:38–42,245–261,329–347,459–472`.

Сценарий:

1. Worker A выполняется.
2. UI отменяет A, выставляет `current=null` и запускает B, **не дождавшись A**.
3. A возвращается из `engine.execute()` и без проверки владельца выполняет `current=null; processNext()`.
4. Запускается C, хотя B ещё работает.

Это воспроизведено тем же подходом — точные тела `removeTask()`/`processNext()` и fake engine с управляемым завершением:

```text
After removing A and finishing old worker: starts=[1, 2, 3],
B still blocked=true, C already started=true
```

У всех workers один `DownloadEngine`, а его `currentThread/currentHttpCall/currentProcess/currentProcessId` общие. Поэтому последующая отмена может затронуть не ту задачу; `finally` старого выполнения может очистить handle нового. Чтение `currentProcess.getInputStream()`/`waitFor()` через общее поле также небезопасно. `volatile` отдельных handles не делает весь протокол атомарным. Очередь `LinkedList` и `current` дополнительно читаются/изменяются из разных потоков без общей синхронизации.

**Исправление:** один event loop/dispatcher для команд очереди и переходов состояния; отдельный execution context на запуск; task ID + generation; callback завершения принимается только от текущего execution. Не освобождать слот до фактического выхода worker. Недостаточно просто добавить `volatile current` или синхронизировать один метод.

### R03. Частичный кэш перевода считается полноценным аудио; возможна подмена между задачами — [Код]

**Где:** `engine/DownloadEngine.java:139–142,233–246,354–356,499–539`; `service/DownloadService.java:25,72`.

Готовность определяется только `exists() && length() > 1000`. HTTP пишет сразу в `vot_audio_<id>.mp3`. Обрыв после нескольких килобайт оставляет файл, и retry пропускает повторное получение/скачивание перевода. Затем FFmpeg получает усечённое аудио; возможны ошибка сборки или успешный, но неполный перевод.

Дополнительно `nextId` после нового процесса снова начинается с 1, а cacheDir может сохранить старые файлы. Новая задача получает старый `vot_audio_1.mp3` / `temp_video_1.mp4`. Ветка склейки проверяет наличие аудио, но **не требует `task.translate`**, поэтому старый перевод может быть наложен даже при выключенном переводе новой задачи.

**Исправление:** UUID рабочего каталога на задание; manifest с video ID, режимом, языком и отметкой завершения; скачивание в `.part`; проверка длины при известном Content-Length и валидности медиа; атомарное переименование только после успешного окончания. Частичный файл не является cache hit. Разделить использование checkpoint при resume и мусор предыдущего запуска.

**Регрессия:** обрыв аудио после 2 КБ → retry; перезапуск процесса с остатками кэша → новая ссылка; original-only при старом translation cache.

### R04. Кооперативная отмена может завершиться состоянием DONE — [Код]

**Где:** `engine/DownloadEngine.java:173–197,499–539,459–472`; `engine/VotClient.java:80–109,137`.

В `downloadFileWithProgress()` обнаружение PAUSED/CANCELLED делает обычный `return`, не сообщает вызывающему коду, что файл не готов. В audio-only ветке следом безусловно выставляется DONE и записывается история. После других длительных операций также нет обязательной проверки cancellation token перед сменой стадии или фиксацией результата.

Физическая отмена HTTP часто даст IOException, но это не гарантирует корректность всех interleavings: ветка успешного `return` существует. VOT-вызов вообще не хранится в `currentHttpCall`, скачивание thumbnail тоже; отменить эти операции через handle engine нельзя.

**Исправление:** специальный результат/исключение отмены; проверки токена между стадиями, перед запуском процессов и перед публикацией; PAUSED/CANCELLED не переходят в DONE. Для VOT и превью — отменяемые calls с конкретным владельцем. Очистка handles в `finally` execution context.

### R05. Коллизии имён и запись в итоговый файл приводят к потере данных — [Код]

**Где:** `engine/DownloadEngine.java:187–189,222–224,272,280,365–380,499–519,556–559`.

Имя зависит от усечённого до 60 символов title и суффикса `(RU)`, но не от video ID, качества, Mix/Dual или Live Voice. Разные ролики и разные версии одного ролика легко имеют одинаковый путь.

- HTTP `FileOutputStream(dest)` обрезает существующий MP3.
- FFmpeg получает `-y` и перезаписывает предыдущий результат.
- Простой yt-dlp может распознать совпавший файл как уже скачанный, а приложение записать DONE/историю для другой ссылки.
- Ошибка/отмена оставляет неполный файл под окончательным расширением.

**Исправление:** явная collision policy (спросить/сохранить версию/переиспользовать только после проверки identity), уникальное имя с video ID и параметрами, staging-файл. Публикация в MediaStore/SAF после проверки медиа; состояние DONE только после успешного commit результата. Не перезаписывать пользовательский файл без согласованной политики.

### R06. Выбранная папка игнорируется; хранилище не соответствует всему диапазону API — [Код + Риск платформы]

**Где:** `ui/ParamsFragment.java:133–143,320–324,345–369`; `engine/DownloadEngine.java:177–179`; [AndroidManifest.xml](app/src/main/AndroidManifest.xml); [file_paths.xml](app/src/main/res/xml/file_paths.xml).

UI предлагает `Download`, `Download/ytrd`, `Movies/ytrd`, `Music/ytrd` и записывает выбор в `task.outputPath`. Engine его не читает и всегда создаёт `Download/ytrd`. Результат затем заменяет значение `outputPath`.

Для публичных raw-path записей:

- На API 26–28 нет `WRITE_EXTERNAL_STORAGE` ни в manifest, ни runtime-запроса — запись в общую память не обеспечена.
- На API 29 при текущем target используется scoped storage; корректного пути через MediaStore/SAF нет.
- На API 30+ некоторые прямые операции с доступными приложению медиа возможны через FUSE, но это **не универсальная гарантия** для произвольных файлов/sidecars, каталогов и сценариев доступа. Проверка на устройстве необходима; нельзя считать весь pipeline совместимым только потому, что один MP4 удалось создать.

`mkdirs()` не проверяется. FileProvider разрешает только `Download/ytrd`: после исправления выбора папки открытие из остальных каталогов также потребует доработки.

**Исправление:** отдельный `Destination` (URI/тип), staging в private storage, публикация через MediaStore Downloads на API 29+ или SAF tree URI с persistable grant. Для API 26–28 — SAF либо корректный legacy permission flow. Хранить content URI результата. Не решать проблему широким `MANAGE_EXTERNAL_STORAGE` без необходимости.

### R07. «Только Wi‑Fi» и остальные настройки ничего не меняют — [Код]

**Где:** [preferences.xml](app/src/main/res/xml/preferences.xml), строки 7–51; `ui/SettingsActivity.java:27–94`; `ui/ParamsFragment.java:224–246,274–286,300–318`.

Настройки `default_quality`, `wifi_only`, `translate_default`, `voice_default`, `audio_mode_default`, `theme` отображаются и сохраняются Preference framework, но в рабочем коде нет чтения этих ключей. Применяется только отдельная `last_download_folder`, и то лишь визуально — см. R06.

Особенно опасно обещание «только Wi‑Fi»: пользователь может получить большой расход мобильного трафика. Качество по умолчанию фактически первое, обычно максимальное, в отсортированном списке. Перевод принудительно сбрасывается в false после анализа, тема всегда тёмная.

**Исправление:** `SettingsRepository`, типизированные настройки и snapshot при создании задания; `NetworkPolicy` перед стартом и при смене сети. Явно решить, распространяется ли ограничение на анализ, VOT, preview и обновление движка. До реализации скрыть/пометить неработающие настройки, особенно Wi‑Fi.

### R08. Миниатюра повторно скачивается на каждом обновлении прогресса — [Код]

**Где:** `ui/DownloadsFragment.java:120–245,330–395,414–455`; `service/DownloadService.java:187–193`.

Каждый `updateUi()` заново вызывает `loadActiveThumbnail()`, а тот создаёт новый Thread, новый OkHttpClient, новый запрос и новый Bitmap. При частых callbacks throttling в 150 мс допускает несколько таких запусков в секунду для одной и той же картинки.

Очередь и ошибки обновляются через `notifyDataSetChanged()`, их bind тоже повторно создаёт загрузки превью. Запросы не отменяются при уничтожении view, нет deduplication и проверки identity holder. Старый ответ может нарисовать картинку другой задачи в переиспользованной карточке.

**Последствия:** лишний мобильный трафик, CPU/GC, память, конкуренция с основной загрузкой. На медленной сети число одновременных потоков особенно растёт.

**Исправление:** lifecycle-aware image loader с memory/disk cache, bounded executor, привязка к URL/holder, placeholder и отмена. Progress обновлять payload-ами, не пересоздавая весь контент списка. Не начинать image loading при неизменившемся thumbnail URL.

### R09. Повтор ошибочной задачи не возвращает foreground-режим — [Код]

**Где:** `service/DownloadService.java:68–77,85–98,127–135,155–165`.

После последней ошибки worker вызывает `processNext()`, очередь пуста → `stopForeground(true); stopSelf()`. Пока Activity bound, объект службы может оставаться доступен. `retryTask()` снова запускает `processNext()`, **но не выполняет `startForegroundService/startForeground`**, в отличие от enqueue. Обычный `.notify()` не делает службу foreground.

Сценарий: единственная задача завершилась ошибкой → «Повторить» → пользователь уходит с экрана. Загрузка может продолжаться без требуемого lifecycle/foreground-сопровождения. После unbind отсутствует гарантированное владение worker службой.

**Исправление:** единый путь `ensureExecutionStarted()` для enqueue/retry/resume, гарантированное foreground-состояние до выполнения. UI не должен запускать работу в потенциально stopped instance через произвольный binder-вызов.

### R10. Очередь не переживает смерть процесса; жизненный цикл службы не завершён — [Код + Риск платформы]

**Где:** `service/DownloadService.java:25–37,51–65,137–183`; весь класс — нет `onDestroy()` и `onTimeout(int,int)`.

Задания существуют только в памяти, возвращается START_NOT_STICKY; нет checkpoint/БД. При process death теряются очередь, paused/error state и связь с частичными файлами. Foreground service снижает вероятность остановки, но не даёт гарантии бессмертия.

При target 35 длительный `dataSync` foreground service на Android 15 подчиняется временному бюджету. Обработчик timeout отсутствует; это отдельный риск остановки/ошибки после исчерпания разрешённого фонового времени, а не утверждение, что каждая короткая загрузка падает. Нет `onDestroy()` для контролируемого закрытия execution. В отмене последней задачи вызывается stopForeground, но не stopSelf в этой ветке; `onStartCommand()` после обработки CANCEL ещё и безусловно вызывает startForeground, что создаёт риск «призрачного» уведомления.

**Исправление:** durable tasks/checkpoints; восстановление как INTERRUPTED с проверкой артефактов; supervisor службы, единый учёт активной работы и foreground state; обработка Android timeout и destroy. Осознанно выбрать механизм user-initiated long downloads для целевых API; не считать замену Service на WorkManager автоматическим устранением всех лимитов.

## 5. Ошибки медиа-pipeline и VOT

### R11. Субтитры не попадают в финальное переведённое видео — P2, [Проверено]

**Где:** `engine/DownloadEngine.java:273–310`.

Sub-file добавляется как input 2, задаётся `-c:s mov_text`, но нет `-map 2:s`. В Mix/Dual используются явные `-map`, поэтому автоматический выбор субтитров не выполняется. Даже если yt-dlp встроил субтитры в input 0, `0:s` тоже не маппится.

**Проверка:** Linux FFmpeg, синтетический MP4 2 секунды + MP3 1 секунда + SRT; воспроизведён выбор потоков из кода. В обеих командах выходной MP4 не содержал ни одного subtitle stream. Это проверка семантики FFmpeg, не Android-бинарника.

**Исправление:** явный mapping выбранного subtitle input/stream, отсутствие двойного embedding, metadata языка по проверенному источнику. Автотест команд плюс `ffprobe` итогового файла. Наличие флага `-c:s` само по себе поток не добавляет.

### R12. Mix теряет оригинальный звук после окончания короткого перевода — P2, [Проверено]

**Где:** `engine/DownloadEngine.java:298–305`.

`amix=inputs=2:duration=shortest` ограничивает смешанную аудиодорожку самым коротким входом. Видео копируется полностью, поэтому в конце может остаться тишина без оригинального звука.

**Проверка:** исходные video/audio — 2 секунды, перевод — 1 секунда. `ffprobe` результата: video=2.000000, audio=1.000000.

**Исправление:** при требовании сохранять весь оригинал использовать `duration=first` (если original первый) или явно согласованный padding/trimming. Нормализацию amix настроить осознанно: коэффициенты volume 0.2/1.2 при default normalization не равны простому обещанию финальных амплитуд 20%/120%. Проверить разные длительности, отсутствие оригинальной audio stream и clipping.

### R13. UI обещает MKV, engine всегда выбирает MP4; ограничения качества имеют обход — P2, [Код + Риск]

**Где:** `ui/ParamsFragment.java:233–242,300–309`; `engine/DownloadEngine.java:203–212,247,272,365`.

При качестве >1080 интерфейс пишет MKV, но task.ext остаётся mp4, yt-dlp получает `--merge-output-format mp4`, временный/итоговый путь тоже MP4. Выбор `bv+ba` не ограничивает кодек H.264/AAC; возможны AV1/VP9/Opus с различной поддержкой устройствами и плеерами. Сам по себе AV1/Opus в MP4 не обязательно означает ошибку FFmpeg, но совместимость не соответствует обещаниям интерфейса.

Последний fallback `/b` в `bv[height<=N]+ba/b[height<=N]/b` уже **не ограничен height** и может скачать выше выбранного качества.

**Исправление:** единая `MediaPlan`/`FormatPolicy`, которая определяет фактический контейнер, кодеки, fallback и UI labels; не делать unlimited fallback без предупреждения. Проверять полученный путь/контейнер, а не только ожидаемое расширение.

### R14. Ошибки и ограничения языка/субтитров маскируются упрощённой логикой — P2, [Код + Риск]

**Где:** `engine/VotClient.java:46–66`; `ui/ParamsFragment.java:274–286,317–318`; `engine/DownloadEngine.java:149–168,215–218,294,401–413`.

- `isLangSupported()` не используется при выборе перевода; известный неподдерживаемый язык UI не объясняет.
- Неизвестный язык становится `en`, длительность — 341 секунд. Это предположение отправляется API как факт; живые трансляции/неполные metadata отдельно не обрабатываются.
- Язык оригинальной дорожки Dual всегда `eng`, даже при испанском/немецком и др.
- Субтитры запрашиваются только `--write-subs`, без `--write-auto-subs`; для роликов только с автоматическими субтитрами флаг пользователя может ничего не дать.
- `findSubtitleFile()` выбирает ru либо последний найденный вариант без строгого порядка; также префикс `temp_video_1` совпадает с `temp_video_10...`, если остался чужой sidecar.

**Исправление:** capability model перевода, отдельное состояние неизвестного языка/длительности, явная политика live; язык дорожек из metadata; политика manual/auto/fallback subtitles и сообщение об отсутствии. Поиск только в каталоге конкретной задачи.

### R15. Protobuf decoder допускает неконтролируемое выделение памяти и принимает повреждённые данные — P2, [Проверено]

**Где:** `engine/VotClient.java:137–146,177–212,217–223,253–299`.

Нет ограничений числа байтов varint, корректного termination, длины сообщения и `len <= remaining`. Length-delimited поле сразу выделяет `new byte[len]`. Unknown wire type просто возвращает накопленные поля, позволяя принять частично разобранный ответ. `resp.body().bytes()` также читает весь ответ в память.

На **исходных Java-методах**, вызванных reflection в JVM с `-Xmx64m`, получены результаты:

| Вход (hex) | Результат |
|---|---|
| `20 01` | `{4=1}`, корректный контроль |
| `20 80` | `{4=0}`, усечённый varint принят |
| `20 01 0F` | `{4=1}`, неизвестный wire type проигнорирован после status |
| `0A 05 41` | `ArrayIndexOutOfBoundsException` |
| `0A FF FF FF FF 07` | `OutOfMemoryError` из-за заявленной длины 2 147 483 647 |

OOM не ловится `catch (Exception)` и способен оборвать worker/процесс. Для эксплуатации нужен контроль/повреждение upstream-ответа, а HTTPS endpoint фиксирован: это прежде всего подтверждённый дефект parser robustness, **не доказанная возможность атаки любым пользователем извне**.

Дополнительно `encodeVarint(-1)` возвращает `[0]`: выражение `1L << 64` в Java сдвигает на 0. Сейчас в request используются неотрицательные значения, поэтому это латентный дефект расширяемости, не основная причина сетевых сбоев.

**Исправление:** protobuf schema + проверенная реализация либо строго bounded parser; типизированная ProtocolError; reject truncation/overflow; лимит response size, varint ≤10 байт; тестовый корпус повреждённых данных. Лечить лимитами, а не попыткой просто поймать OOM.

### R16. Polling не восстанавливается после временной сетевой ошибки — P2, [Код]

**Где:** `engine/VotClient.java:80–110,121–154`; `engine/DownloadEngine.java:50–64,499–554`.

30 попыток относятся к Waiting, а не к network retry: первый HTTP 429/5xx или IOException даёт `success=false` и завершает весь polling. Нет Retry-After, backoff/jitter или общего дедлайна. На последней Waiting-попытке происходит ещё один sleep, хотя следующего запроса уже не будет. HTTP-загрузка перевода не имеет собственного recovery/resume.

`fetchInfo()` на любую ошибку пробует обновить nightly yt-dlp, включая offline/private/deleted video; это неадекватная классификация причины, добавляющая задержку и трафик.

**Исправление:** различать transient/permanent/protocol/cancelled; ограниченный retry только для временных ошибок, respect Retry-After, общий deadline и отменяемое ожидание; обновлять yt-dlp только по отдельной политике.

### R17. Инициализация и обновление yt-dlp не имеют общего барьера готовности — P2, [Код + Риск]

**Где:** [App.java](app/src/main/java/io/github/idex/ytrdroid/App.java), строки 21–45; `engine/DownloadEngine.java:50–73`; `ui/SettingsActivity.java:43–77`.

App начинает init/FFmpeg init/update в отдельном Thread. UI и engine не ждут ready/failure и могут работать сразу. Обновления инициируются из трёх мест: App, fetchInfo fallback, Settings. Нельзя по этому коду гарантировать, что все внутренние операции библиотеки конфликтуют — часть может быть синхронизирована внутри зависимости, — но приложение не контролирует readiness/version/update-in-progress и не запрещает обновление во время загрузки.

**Исправление:** `RuntimeManager` с наблюдаемым состоянием и shared initialization future; single-flight update, throttling, выбранный канал, запрет замены runtime во время активных execution; сохранять последнюю рабочую версию. Ошибку init показывать пользователю, а не только в Logcat.

## 6. Файлы, история, UI и поддерживаемость

### R18. Очистка кэша удаляет рабочие файлы активной загрузки — P1, [Код]

**Где:** `ui/SettingsActivity.java:81–92`; `engine/DownloadEngine.java:139,247,354–356`; `ui/DownloadsFragment.java:304–315`.

Кнопка «Очистить кэш» вызывает `delete()` для всех непосредственных файлов cacheDir без проверки активных задач. Там лежат текущие video/translation/subtitles. Удаление может случиться между стадиями или перед открытием файла FFmpeg. При отсутствии рекурсивного обхода часть будущих каталогов, наоборот, не очистится, но интерфейс всё равно покажет «Очищено». `listFiles()` может вернуть null.

На error/cancel рабочие файлы централизованно не удаляются; очистка после success касается лишь части sidecars. Кнопка удаления error-task пытается удалить `task.outputPath`, который до успеха ещё может быть **каталогом назначения**, а не файлом; текущий `File.delete()` не рекурсивен, но это неверная и опасная семантика.

**Исправление:** `WorkspaceManager`, разделение disposable image cache и checkpoints, защита active workspaces, уборка orphan-каталогов по правилам возраста/состояния, проверка результатов удаления. Удаление ошибки не должно оперировать полем destination как result file.

### R19. История теряет разные варианты одного видео; запись неатомарна — P2, [Код]

**Где:** `engine/DownloadEngine.java:475–494`; `model/HistoryManager.java:41–80`.

ID — `String.valueOf(task.url.hashCode())`, а `addOrUpdate` удаляет всё с тем же id **или** filePath. Аудио и видео одной ссылки имеют одинаковый id, поэтому новая загрузка вытесняет старую карточку, хотя старый файл остаётся. Hash collision между разными URL также возможен. Параметры Mix/Dual/LiveVoice/subtitles не сохраняются; `duration/uploader` в модели есть, но engine их не заполняет.

`FileWriter(history.json)` сразу обрезает файл: авария/нехватка места оставляет повреждённый JSON. Ошибка save проглатывается, UI не знает, что persistence не состоялся. Загруженные элементы не валидируются: например, `[null]` позже приводит к NPE при обходе/сортировке.

**Исправление:** отдельный UUID результата и video ID как атрибут; одна запись на конкретный артефакт, все параметры запроса; Room либо AtomicFile/temp+rename с валидируемой схемой и версией. Не превращать ошибку истории в ложную ошибку скачанного файла, но показать предупреждение и возможность восстановить индекс.

### R20. Удалённая из списка запись возвращается; импорт принимает мусор за готовое видео — P2, [Код]

**Где:** `model/HistoryManager.java:28–32,83–101,104–147`; `ui/FilesFragment.java:143–158`.

«ОК» в диалоге удаляет только запись, сохраняя файл, но при следующем создании HistoryManager `importExistingDiskFiles()` снова импортирует любой отсутствующий в истории файл. Таким образом, удаление записи не сохраняется после перезапуска процесса.

Импорт не фильтрует `.part`, `.ytdl`, субтитры и другие незавершённые/не-медиа файлы. URL восстановить из имени нельзя; «Повторить» подставляет title, который обычно не проходит проверку YouTube URL. При «С файлом» результат `delete()` игнорируется, запись удаляется и Toast обещает успех, даже если файл остался.

**Исправление:** различать реестр успешных результатов и просмотр каталога; явный импорт только валидных завершённых медиа; tombstone/hidden-state для удаления из истории либо другой согласованный UX. Проверять результат удаления; для imported item без URL скрывать повтор загрузки или просить ссылку.

### R21. Список файлов не обновляется при завершении загрузки, если экран уже открыт — P2, [Код]

**Где:** `ui/FilesFragment.java:51–77`; `ui/MainActivity.java:27–33`; `model/HistoryManager.java:73–80`.

FilesFragment читает историю в `onViewCreated/onResume`, но не подписан на её изменения. Если завершение происходит, пока пользователь остаётся на экране файлов, новый результат не появляется до повторного входа/resume. Единственный listener службы предназначен DownloadsFragment.

**Исправление:** наблюдаемый repository результатов и lifecycle-aware подписка; `ListAdapter/DiffUtil`. Завершённые задачи в service тоже не следует хранить бесконечно в `tasks`: DONE не отображаются, но продолжают накапливаться до уничтожения сервиса.

### R22. Миниатюры файлов блокируют main thread, имеют большой cache и гонку holder — P2, [Код]

**Где:** `ui/FilesFragment.java:42,218–282`.

Локальные JPEG декодируются в `onBindViewHolder` на UI thread без downsampling. `LruCache<>(50)` ограничивает число bitmap-объектов, **не байты**. Fallback `getFrameAtTime()` может вернуть полноразмерный кадр: 4K ARGB bitmap — примерно 32 МиБ, то есть 50 объектов — потенциально больше гигабайта. Это оценка худшего случая, не измеренный расход текущего запуска.

Асинхронная генерация пишет в target без проверки текущего path holder; MediaMetadataRetriever не закрывается в finally при исключении. Путь как cache key не учитывает замену файла по тому же имени.

**Исправление:** ограничение памяти в байтах, scaled thumbnails, background decoding, bounded executor, lifecycle/identity guards, гарантированное закрытие retriever, invalidation по изменению файла.

### R23. Анализ ссылки не управляется lifecycle и не имеет видимого retry — P2, [Код + Риск]

**Где:** `ui/ParamsFragment.java:89–130,180–220,253–270`; `ui/SettingsActivity.java:52–73`; `ui/MainActivity.java:108–112`.

`analysisGeneration` отбрасывает часть старых результатов, но не останавливает уже запущенные yt-dlp процессы. Быстрое редактирование/закрытие/повторное открытие диалога может создать несколько анализов и конкурирующих обновлений. Состояние анализа не хранится в ViewModel/SavedStateHandle, конфигурационные изменения повторяют работу.

Кнопка analyze с самого начала `GONE` и больше не становится VISIBLE; после сетевой ошибки пользователю нужно менять URL, чтобы запустить повтор. Некорректная ссылка при auto-analysis просто не проходит условие и не получает понятной ошибки. Thumbnail callback не проверяет generation, поэтому может показать старое превью для новой ссылки. В Settings после post на UI вызывается `requireContext()` без повторной проверки attached-state, что даёт lifecycle-race при уходе с экрана.

**Исправление:** ViewModel + отменяемый single-flight анализ, сохранение состояния ввода/параметров, явные состояния Ready/Loading/Error и доступная кнопка Retry. Для всех callbacks — привязка к lifecycle конкретной view и generation/request ID.

### R24. URL-parser принимает посторонний домен и лишний суффикс ID — P2, [Проверено]

**Где:** [UrlUtil.java](app/src/main/java/io/github/idex/ytrdroid/util/UrlUtil.java), строки 7–22.

Regex использует `find()` без границы hostname и без проверки окончания video ID. На исходном Java-коде:

```text
https://notyoutube.com/watch?v=abcdefghijk  → abcdefghijk
https://youtube.com/watch?v=abcdefghijkMORE → abcdefghijk
```

`watch\?.*v=` также слишком широко трактует параметры. Сейчас ParamsFragment канонизирует URL до настоящего youtube.com, поэтому это **не доказательство SSRF или запроса к атакующему домену**. Дефект — неверное принятие ввода и возможность скачать не то видео, которое подразумевал пользователь.

**Исправление:** сначала извлечь URI из текста, затем строго проверить scheme/host, route и query parameter `v`; валидировать ID целиком. Тесты на youtu.be/watch/shorts/embed/live, m/www, query order, чужие домены, несколько ссылок и длинный ввод.

### R25. Обработка ошибок не даёт достаточной диагностики — P2, [Код]

**Где:** `engine/DownloadEngine.java:105–123,329–351,389–398,495–554`; `model/HistoryManager.java:57–64`; UI catch-блоки.

FFmpeg stderr объединён со stdout, но строки, не являющиеся `out_time_us`, отбрасываются. При ненулевом exitCode остаётся только «FFmpeg failed with exit code N», без причины — codec/storage/input. Нет стадии и recoverability в типе ошибки; UI показывает произвольный `e.getMessage()`, иногда null или длинный технический текст.

Gson-ошибка переключает metadata на ручной поиск строк: он некорректен для escaped quotes, Unicode escapes, null и вложенных полей. Ошибочный/неожиданный JSON может превратиться в частично успешный VideoInfo с потерянной duration, вместо явной ProtocolError. Многие `catch (Exception ignored)` и непроверенные `mkdirs/delete` скрывают причины.

**Исправление:** ошибки `Network/Storage/Protocol/TranslationUnavailable/ExternalTool/Cancelled` со stage и retry policy; bounded stderr tail; структурированные логи с task/execution ID; корректный JSON parser без эвристического «успеха» на повреждённых данных. Проверять фактический результат yt-dlp/ffprobe до DONE.

### R26. Устаревшая документация и неактивный код вводят агентов в заблуждение — P2, [Код]

**Где:** [README.md](README.md), родительские `../README.md`, `../AGENTS.md`; `ui/DownloadFragment.java:87–102`; `ui/MainActivity.java:22,115–119`; `res/menu/bottom_nav.xml`; `gradle/libs.versions.toml`.

Android README заявляет Chaquopy, Python bridge, отсутствие wrapper/FFmpeg и другой способ output. Сейчас всё это не соответствует фактическому проекту. Родительский AGENTS ориентирован на CLI, содержит устаревшие commit/version/test-count и не описывает Android.

Есть второй `DownloadFragment`, который не открывается из текущей навигации; он использует старую схему replace для ParamsFragment, хотя основной экран показывает его как bottom sheet. `pendingUrl` нигде не присваивается, но существует consume-метод. Неиспользуемое bottom-nav меню, step icons и строковые ресурсы создают ложные точки расширения; version catalog пуст. Lint подтвердил 23 неиспользуемых ресурса.

**Исправление:** актуальный Android README и локальный AGENTS с картой runtime/потоков/хранилища/сборки; обозначить границу CLI и Android; после проверки удалить мёртвые маршруты и ресурсы. Не оставлять «planned» функции описанными как работающие.

### R27. UI-ресурсы и доступность требуют систематизации — P3, [Lint + Код]

Много строк захардкожено в Java/XML, используются literal colors, `quality + "p"` даёт `audiop/autop`, размеры touch targets часто 36–44dp вместо удобных 48dp. Есть отсутствующие contentDescription, RTL-несогласованности; экраны требуют проверки с TalkBack, большим шрифтом, keyboard и Android 15 insets (особенно Settings).

Все launcher PNG имеют одинаковые 1254×1254 пикселя в пяти density-каталогах; lint отмечает дублирование и несогласованный dp-размер. Нет полноценного adaptive icon. `ic_logo_brand.png` лежит в densityless `drawable`, что может вести к нежелательному scaling.

**Исправление:** string/plural resources, единые форматтеры качества/размера, theme tokens/dimens, корректные иконки/density или vector/adaptive assets. Не делать механическую замену всех DefaultLocale: UI-числам подходит Locale.getDefault(), внутренним именам/протоколу — Locale.ROOT.

## 7. Безопасность, зависимости и поставка

### S01. Конфигурация VOT и приватность логов — P2

`engine/VotClient.java:30–32` содержит фиксированный HMAC-ключ и browser User-Agent; значение ключа намеренно не воспроизводится в отчёте. Ключ, встроенный в APK, нельзя считать секретом. Его действительность зависит от неофициального API, возможны смена протокола/ограничения.

`engine/DownloadEngine.java:151,164` пишет URL видео и полный URL аудио перевода в Logcat. Такой URL может содержать временные параметры доступа; экспортируемая диагностика должна их редактировать. Не утверждается, что любой сторонний Android-app имеет доступ ко всему Logcat.

`allowBackup=true`, но нет отдельной политики backup/data-extraction. История содержит просмотренные/скачанные URL и пути; при backup/restore на другое устройство пути могут быть невалидны. Нужны осознанная политика приватности и обработка восстановления; фактическое облачное копирование зависит от устройства и настроек пользователя.

### S02. Автообновление nightly меняет runtime независимо от APK — P2

App пытается обновить yt-dlp на каждом холодном старте, Settings и metadata fallback тоже инициируют обновление. APK version уже не полностью определяет исполняемый код. Нужны фиксируемая версия runtime в диагностике, выбранный канал, single-flight update, проверка происхождения/целостности по контракту библиотеки, возможность rollback и политика consent/Wi‑Fi. Проверка внутренней реализации механизма update зависимости в этот аудит не входила.

### S03. Нет Android CI/тестов; release-поставка не проверяется — P1 как quality gate

В `app/src` только `main`, нет `test/androidTest`; `testDebugUnitTest` сообщает **NO-SOURCE**. Родительский `.github/workflows/ci.yml` запускает только Python pytest. Успех CLI-тестов ничего не доказывает о Java pipeline.

`android-app/` не отслеживается Git: текущий upstream/CI не сможет воспроизвести именно этот Android-код без включения его в VCS. Это состояние рабочего дерева, а не ошибка самого Java-кода; commit/add без запроса не выполнялись.

Release build имеет `minifyEnabled false`, не описаны signing/release steps. Отсутствие hardcoded signing credentials — правильно; но нужен документированный безопасный процесс выпуска. Wrapper не содержит `distributionSha256Sum`, dependency verification/locking в проекте не обнаружены. Это hardening-рекомендации, не доказательство компрометации.

### S04. Размер APK, native-совместимость и лицензии — P2/P3

- Текущий universal debug APK — примерно **154 МиБ**, содержит arm64-v8a, armeabi-v7a, x86_64. Размер объясняется bundled runtimes, но для поставки нужны AAB/ABI splits и измерение installed/extracted size.
- В проверенных верхнеуровневых arm64 ELF (`libffmpeg.so`, `libffprobe.so`, `libpython.so`, `libqjs.so`) LOAD alignment = `0x4000` (16 КиБ). **Нельзя записывать им неподтверждённый баг 16KB alignment.** Содержимое всех runtime zip, APK alignment и фактический запуск на 16KB-device целиком не проверялись.
- Native execution использует внутренние пути `noBackupFilesDir/youtubedl-android/packages/...` в `DownloadEngine.java:315–327`. Это хрупкая связь с layout зависимости; изолировать в адаптере и проверять upgrade-тестом.
- Есть лицензия Material Icons, но полный состав лицензий FFmpeg build/codecs, yt-dlp, Python и остальных компонентов требует отдельного SBOM/notice-аудита. MIT-лицензия родительского проекта не заменяет лицензионные условия бинарных зависимостей.

## 9. Рекомендуемая архитектура без избыточного усложнения

**Не требуется срочно переходить на Kotlin/Compose, создавать много Gradle-модулей или внедрять большой DI-framework.** Главная цель — изолировать чистую логику, владение состоянием и побочные эффекты. На первом этапе достаточно одного app-модуля с ясными пакетами и constructor injection.

```text
ui/
  screen + ViewModel + immutable UiState
application/
  DownloadCoordinator       # единственный владелец очереди/state machine
  AnalyzeVideoUseCase
  DownloadPipeline          # композиция этапов, не Android UI
  TaskRecovery
model/
  DownloadRequest           # immutable пользовательский запрос
  TaskSnapshot              # наблюдаемое immutable состояние
  DownloadResult            # published URI, metadata
  Stage / DownloadError
ports/
  VideoSource, TranslationProvider, MediaProcessor
  TaskRepository, ResultRepository, DestinationWriter
  RuntimeManager, NetworkPolicy, Clock
infrastructure/
  ytdlp/, vot/, ffmpeg/, storage/, persistence/, runtime/
service/
  Android foreground lifecycle + notification adapter
```

### Обязательные инварианты

1. При последовательной очереди **не более одного active execution**; новый запускается только после фактического завершения старого.
2. Задачу изменяет один coordinator; UI получает snapshots, а не mutable `DownloadTask`.
3. `executionId` отличает retry от предыдущего запуска той же задачи; старые callbacks игнорируются.
4. PAUSED/CANCELLED не становятся DONE от остаточного callback.
5. `destination` и `publishedResultUri` — разные поля и разные типы.
6. Частичный файл никогда не является готовым артефактом или успешным cache hit.
7. DONE означает: медиа проверено, публикация закончена; ошибка индексации истории отражена отдельно.
8. Кэш одной задачи не читается другой; cleanup не удаляет активный workspace.
9. Все пути выполнения, включая retry/resume, имеют одинаковое lifecycle/foreground сопровождение.
10. Сохранённые настройки или реально применяются, или не предлагаются UI.

### Пример состояния

```text
QUEUED → WAITING_FOR_RUNTIME/NETWORK → TRANSLATING
       → DOWNLOADING → PROCESSING → PUBLISHING → DONE

active → PAUSING → PAUSED → QUEUED
active → CANCELLING → CANCELLED
active → ERROR → QUEUED (новый executionId)
process death → INTERRUPTED → проверка checkpoint → retry/resume
```

Состояния можно упростить, но нельзя смешивать запрос остановки с уже подтверждённой остановкой. Resume у HTTP/FFmpeg не обязан означать точное продолжение с байта/кадра: это нужно явно определить. Если реально поддерживается только перезапуск этапа, интерфейс должен это честно отражать.

### Границы тестирования

- `FfmpegCommandBuilder` — чистая функция `MediaPlan → argv`.
- `VotProtocolCodec` — bytes ↔ typed response, без Context/Logcat/HTTP.
- `QueueStateMachine` — команды и events → новое состояние, без Thread/Service.
- `DestinationWriter` — stage/validate/publish/abort.
- `WorkspaceManager` — создание/проверка/checkpoint/cleanup.
- `SettingsRepository` — преобразует Android preferences в типизированный snapshot.

Так агент сможет менять одну ответственность, зная, какие тесты защищают контракт, а не искать связанные строковые условия по всем Fragment/engine/service.

## 13. Итоговое решение

Архитектуру можно довести до устойчивой **постепенным рефакторингом**, сохранив Java, XML UI и существующие библиотеки. Основные проблемы — не язык и не внешний вид, а отсутствие формальных контрактов состояния, владения ресурсами и фиксации результатов.

До стабильного релиза приоритетны: **очередь/отмена → целостность файлов и storage → реально работающие настройки → lifecycle/recovery → медиа-корректность → тесты и диагностика**. Обновление дизайна и устранение мелких lint-предупреждений не должны маскировать эти блокеры.

**Ограничение вывода:** успешная incremental debug-сборка и lint подтверждают сборочную состоятельность текущего окружения, но не гарантируют работоспособность загрузок на устройстве, доступность неофициального VOT API или отсутствие других ошибок. Перечисленные непроверенные платформенные сценарии должны быть закрыты тестами перед выпуском.
